## 1. 概要

### 1.1 背景

メタバースサーバー（meta-server）の総合性能を、運用者がメンテナンス時間帯に手動で評価する仕組みがない。ハードウェア・同期・DB・音声／映像配信の負荷を一括で計測し、カテゴリ別スコアと HTML レポートとして残す必要がある。

### 1.2 目的

addon `meta-benchR1` により、本番と同一 Node プロセス上でベンチマークを実行し、運用者が管理画面から開始・結果確認できるようにする。プレイヤー bot は手元の別 PC で常駐する **Bench Runner** が担当する。

### 1.3 基本方針

| 項目 | 方針 |
|------|------|
| 版 | 第1版（R1）。将来 R2 以降で拡張可能な設計 |
| 対象ユーザー | **運用者のみ**（開発者向け常時監視・一般ユーザー向け自己診断は対象外） |
| 評価形式 | **カテゴリ別スコア**（各 0–100、**高いほど良い**） |
| 合格／不合格 | R1 では **閾値判定なし**（スコア表示のみ） |
| レポート言語 | **日本語のみ** |
| 実行 | 管理画面から **手動**、所要 **3〜5 分** |
| 再現性目標 | 同一マシンで **±5〜7%**（bot・WebRTC 系はぶれやすい点に留意） |
| クライアント計測 | **含めない**（FPS・描画・ブラウザは R1 対象外） |
| コア改修 | **許容**（メンテナンスモード、bot 用 API、tick 計測等） |
| addon 状態 | ベンチ前に **meta-benchR1 のみ有効**とし、**プロセス再起動後**に実行（[アドオン再起動ポリシー](addons-restart-policy.md) に準拠。実行中の動的無効化はしない） |

### 1.4 命名

| 名称 | 意味 |
|------|------|
| meta-benchR1 | メタバースサーバー総合ベンチマーク第1版 |
| Bench Runner | 手元別 PC で常駐する bot 実行サーバー |

## 2. 確定仕様（ステークホルダー決定事項）

| # | 項目 | 決定内容 |
|---|------|----------|
| D-01 | 実行プロセス | **本番と同一 Node プロセス**（メンテ時間に手動実行） |
| D-02 | 新規実ユーザー Socket | **即拒否**（エラーコード + 日本語メッセージ） |
| D-03 | 既存接続中の実ユーザー | **アラートで警告** + **接続維持**（強制切断しない） |
| D-04 | ベンチ中の接続許可 | **admin**（管理画面・メタバース admin 入室）および **bench bot** のみ追加許可 |
| D-05 | 異常終了時 | **メンテナンスモード OFF を必ず実行**（`finally` 相当の保証） |
| D-06 | TPS 理論 max | **約 30 tick/s**（現行 `server.js` の `players-update` 33ms 間隔と一致） |
| D-07 | 音声・メディア | **VC + PDF VC + ビデオ VC** を R1 **すべて必須** |
| D-08 | Runner 配置 | **手元の別 PC**、常駐 **Runner サーバー**を起動した状態で管理画面からベンチ実行 |
| D-09 | bot ユーザー | **実行時に一時ユーザー自動作成**、ベンチ後削除。生徒・教師アカウントは使わない |
| D-10 | 同時 bot 数 | **設定可能**（例: 20 / 50 / 100、既定 50） |
| D-11 | レポート保存 | addon 専用ディレクトリ `addons/meta-benchR1/reports/`、`benchreportYYYYMMDD-HHMM.html` |
| D-12 | レポート自動記載 | サーバスペック、meta-server バージョン、有効 addon 一覧 |
| D-13 | 有効 addon | ベンチ実行前は **meta-benchR1 のみ有効**とし、設定反映のため **Node プロセスを再起動**してからベンチを開始する（動的アンロードは行わない） |
| D-14 | 管理 API パス | 運用者向け HTTP API は **`/admin/addons/meta-benchR1/...`** に統一（サーバー側 Basic 認証）。Runner・bot 向けは **`/api/addons/meta-benchR1/...`** |

## 3. スコープ

### 3.1 対象（In Scope）

- サーバ CPU 計算ベンチ（マルチコア: Worker Threads / child_process）
- サーバ RAM 512MB 読み書きベンチ（checksum 整合性・速度・レイテンシ）
- 外部 Runner による同時ログイン bot（移動・ジャンプ・ping・接続維持率）
- サーバ tick 実測と TPS 差分（max 30 tick/s − 実測）
- SQLite クエリ時間（`users.db` / `addons_registry.db` / **読み込み中 addon** の DB。D-13 により通常は `meta-benchR1` のみ）
- VC / PDF VC / ビデオ VC の 10 bot 配信・subscribe・mediasoup stats
- 管理画面専用タブ（Runner 状態・実行・進捗・スコア）
- HTML レポート生成（日本語）
- Bench Runner（登録・ジョブ受信・bot プール）

### 3.2 対象外（Out of Scope / 非目標）

- 本番への **常時負荷**（定期自動ベンチ・常駐監視）
- **他サーバとの横比較**・ランキング
- **サービス停止に至るストレステスト**
- クライアント側ベンチ（FPS・描画・Three.js・WebXR）
- 合格／不合格の自動閾値判定（R1）
- 英語／多言語レポート

## 4. システム構成

```
┌──────────────────────────────────────────────────────────────┐
│  meta-server（本番プロセス）                                      │
│  ├─ メンテナンスモード（D-02〜D-05）                               │
│  ├─ meta-benchR1 addon（**再起動後にのみ読み込み**。他 addon は無効）      │
│  │    ├─ hw-cpu / hw-mem / db-sqlite / tick 集計（同一プロセス）    │
│  │    ├─ run 管理・スコア・HTML レポート                           │
│  │    └─ Runner 登録・ジョブ配信 API                               │
│  └─ コア Socket.io / mediasoup（既存プロトコル）                   │
└────────────────────────────┬─────────────────────────────────┘
                             │ HTTPS + WSS + WebRTC (UDP/TCP)
                             ▼
┌──────────────────────────────────────────────────────────────┐
│  手元の別 PC — Bench Runner（常駐）                                │
│  ├─ 本番へアウトバウンド登録（pull モデル）                          │
│  ├─ socket.io-client × N（接続・移動・ping）                       │
│  └─ mediasoup-client（Node）× 10 — VC / PDF / Video           │
└──────────────────────────────────────────────────────────────┘
         ▲
         │ 運用者ブラウザ（admin / 管理画面）
         └─ ベンチ開始・進捗・レポート閲覧
```

### 4.1 addon 配置（想定）

```
addons/meta-benchR1/
├── plugin.json
├── server.js
├── config.json.example
├── migrations/
├── client/
│   └── admin.js          # registry-admin.js から import
├── runner/
│   ├── serve.js          # Runner 常駐サーバー CLI
│   ├── socket-bot-pool.js
│   └── mediasoup-bot-pool.js
└── reports/              # benchreportYYYYMMDD-HHMM.html
```

### 4.2 ベンチ前の addon 準備（再起動前提）

本プロジェクトは addon の有効／無効が **プロセス再起動後にのみ反映**される（[アドオン再起動ポリシー](addons-restart-policy.md)）。ベンチ中に他 addon を動的に外すことはできない。

1. 管理画面 `/admin.html` の「アドオン」で、**`meta-benchR1` 以外をすべて無効**にする
2. **`meta-benchR1` のみ有効**であることを確認する
3. **Node プロセスを再起動**する（`systemd` / PM2 / 手動など運用に合わせる）
4. 再起動後、読み込み addon が `meta-benchR1` のみであることをプリフライト（P-07）で確認してからベンチを開始する

ベンチ完了後、通常運用に戻す場合は必要な addon を再有効化し、**再度プロセス再起動**する。

### 4.3 Bench Runner の運用フロー

1. **§4.2 の addon 準備・再起動を完了**していること
2. 手元 PC で `runner serve` を起動（常駐）
3. Runner が本番へ **アウトバウンド**で登録（NAT 内 PC でも可）
4. 管理画面に「Runner: 接続済み」と表示
5. 運用者が「ベンチ開始」→ プリフライト合格後、メンテ ON → ジョブ配信
6. Runner が bot 実行、メトリクスを本番へ送信
7. 本番側ベンチと並行実行 → 集計 → HTML → クリーンアップ → **メンテ OFF**

起動例（イメージ）:

```bash
node addons/meta-benchR1/runner/serve.js \
  --server=https://example.com \
  --secret=<RUNNER_SECRET> \
  --name=desk-pc-01
```

## 5. メンテナンスモード

ベンチ run の開始から終了（正常・異常・手動中止を問わず）まで有効とする。

### 5.1 接続制御

| 対象 | 挙動 |
|------|------|
| **新規・実ユーザー** Socket | **即拒否**。エラーコード `BENCH_MAINTENANCE`、日本語メッセージ「現在ベンチマーク実行中のため接続できません。しばらくしてから再度お試しください。」 |
| **既存・実ユーザー** Socket | **維持**。サーバから `bench-maintenance-warning` を emit し、クライアントはアラート／トーストで警告表示（接続は切らない） |
| **admin** | 管理画面（Basic 認証）・メタバース admin 入室（`adminToken`）は **常に許可** |
| **bench bot** | `benchToken` 付き handshake のみ許可。`socket.data.isBenchBot = true` |

### 5.2 異常終了時の保証

次のいずれでも **必ず** メンテナンスモードを OFF に戻す:

- ベンチ正常完了
- 運用者による手動中止
- Runner 切断・タイムアウト
- サーバ側未処理例外

実装は run 単位の `try/finally` およびプロセスレベルのフェイルセーフ（run タイムアウト 6 分）で二重化する。

## 6. プリフライト（ベンチ開始前チェック）

**すべて満たさない場合は開始ボタンを無効化し、不足理由を日本語表示する。**

| # | 条件 | 推奨既定 |
|---|------|----------|
| P-01 | Bench Runner が登録済み | 最終 heartbeat **30 秒以内** |
| P-02 | 他 run が実行中でない | **同時 1 run のみ** |
| P-03 | メンテナンスモードを ON にできること | 既に他理由でメンテ中なら警告 |
| P-04 | レポート保存先の空き容量 | **最低 50 MB** |
| P-05 | mediasoup / VC 系が起動済み | ワーカープール初期化済みフラグ |
| P-06 | 設定 `botCount` | Runner が宣言する **推奨 max** 以下 |
| P-07 | 読み込み addon が `meta-benchR1` のみ | 再起動後の有効 addon 一覧と一致（他 addon が有効なら **開始不可** + 再起動手順を日本語表示） |

## 7. 計測カテゴリとスコア

### 7.1 カテゴリ一覧

| ID | 名称 | 実行場所 | 主な入力 |
|----|------|----------|----------|
| `hw-cpu` | CPU 計算 | 本番 Node | マルチコア含むスループットスコア |
| `hw-mem` | メモリ I/O | 本番 Node | 512MB 読み書き速度・レイテンシ・checksum 整合 |
| `mv-connect` | 接続・同期 | Runner PC | 接続維持率、ping RTT（bot 計測） |
| `mv-tps` | TPS | 本番 Node | max 30 tick/s − 実測 tick/s（差分 0 が健全） |
| `mv-degrade` | 性能劣化指数 | 本番 Node | 下記加重合成 |
| `db-sqlite` | データベース | 本番 Node | 全対象 DB のクエリ時間 |
| `audio-vc` | 音声・メディア | Runner PC | VC / PDF VC / Video VC 各サブスコア |

### 7.2 TPS・性能劣化

- **理論 max**: **30 tick/s**（`players-update` の 33ms `setInterval` に連動。間隔変更時は max も設定連動）
- **実測**: ベンチ中、ルームごとに秒あたりの emit 回数を集計
- **TPS 差分** = `30 − 実測tickPerSec`（負の場合は 0 にクランプ）
- **健全**: 差分 = 0

**`mv-tps` スコア（0–100）**:

```
tpsScore = clamp(0, 100, 100 × (1 − 差分 / 3))
```

差分 3 tick/s 以上で 0 点（約 10% 欠落相当）。

**`mv-degrade` スコア（0–100）**:

| 成分 | 重み | 算出 |
|------|------|------|
| TPS | 50% | `mv-tps` と同式 |
| CPU 負荷上昇 | 30% | ベンチ前 30 秒平均 CPU 比。+0% → 100、+50% → 0（線形） |
| レイテンシ | 20% | bot ping p95。≤50ms → 100、≥300ms → 0（線形） |

### 7.3 bot 仕様（Runner）

| 項目 | 内容 |
|------|------|
| 認証 | 本番が発行する短命 `benchToken`（`socket.handshake.auth`） |
| 接続維持 | **0〜120 秒**（ランダム）。全体 3〜5 分枠内で完結 |
| ワールド | 登録済みワールドから **ランダム** |
| スポーン | **ランダム** |
| 移動・ジャンプ | **実プレイヤーと同じ** Socket イベント・更新レート |
| ping | **bot 自身**が `report-ping` 相当で RTT 計測 |

### 7.4 SQLite（`db-sqlite`）

**対象 DB**:

- コア `users.db`
- `addons_registry.db`
- ベンチ開始時点で **プロセスに読み込まれている addon** の DB（D-13 により **`meta-benchR1.db` のみ**が対象。他 addon は無効のため N/A）

**クエリ**:

- 代表 SELECT（ユーザー数 COUNT、addon 設定読み取り等）
- INSERT テスト行 → DELETE（書き込み）

**スコア**: 全 DB・全クエリの **最悪（最大）レイテンシ** を代表値とする。≤5ms → 100、≥200ms → 0（線形）。addon DB が無効・存在しない場合は **N/A**（カテゴリ表示「対象外」、総合スコア計算から除外）。

### 7.5 音声・メディア（`audio-vc`）

| 項目 | 内容 |
|------|------|
| R1 必須 | **通常 VC**、**PDF VC**、**ビデオ VC** の 3 系統 |
| bot 数 | **10**（全員 producer + consumer、互いに subscribe） |
| 損失 | mediasoup **transport stats**（`packetLoss` 等） |
| サブスコア | `audio-vc-voice` / `audio-vc-pdf` / `audio-vc-video` を各 0–100 |
| 合成 | **均等加重**（3 分割平均） |

各サブスコア: 全 bot ペアの packetLoss 平均 ≤0.5% → 100、≥5% → 0（線形）。到達不能（consumer 未確立）は 0 点。

### 7.6 その他カテゴリの正規化（推奨）

| ID | 正規化（0–100、高いほど良い） |
|----|------------------------------|
| `hw-cpu` | 初回校正 run のスコアを 80 点基準とする相対式、または絶対 ops/s から線形（実装時に校正定数を `config.json` で保持） |
| `hw-mem` | 読み書き MB/s と checksum 成功を合成（速度 70% + 整合性 30%。整合性失敗時 0） |
| `mv-connect` | 接続維持率 60% + ping p95 40%（維持率 100%→60 点満点枠、ping ≤50ms→40 点満点枠） |

**総合スコア（参考表示）**: N/A を除くカテゴリの **単純平均**（R1 は参考値、閾値判定なし）。

## 8. フェーズ失敗・中断

| 項目 | 推奨既定 |
|------|----------|
| 手動中止 | 管理画面に **「ベンチ中止」** ボタンあり |
| Runner 切断 | run を **失敗終了**。Runner 担当カテゴリは **0 点または N/A**、サーバ側は完了分を計測し **部分レポートを必ず生成** |
| `audio-vc` 部分失敗 | 失敗系統のみサブスコア 0、他は実測値で合成 |
| 一時ユーザー削除失敗 | **3 回リトライ**、失敗時は管理画面とレポートに **要手動削除** と runId 一覧を記載 |
| HTML レポート | **部分成功でも必ず出力**（ステータス: `completed` / `partial` / `failed`） |

## 12. API 概要（実装指針）

HTTP は用途ごとにプレフィックスを分ける（`nfc-spawn` / `admin-reboot` と同様の慣習）。

### 12.1 管理 API（運用者・管理画面）

プレフィックス: **`/admin/addons/meta-benchR1/`**  
認証: サーバー側 **`basicAuth`**（`app.use('/admin', basicAuth)` により `/admin` 配下で強制）

| メソッド | パス | 用途 |
|---------|------|------|
| GET | `runner/status` | Runner 状態（接続・heartbeat・推奨 max bot） |
| GET | `runner/pairing-code` | 6 桁ペアリングコード発行（10 分有効） |
| POST | `runs` | ベンチ開始 |
| GET | `runs/:id` | 進捗・スコア |
| POST | `runs/:id/abort` | 手動中止 |
| GET | `reports/:filename` | HTML ダウンロード |

管理画面の `client/admin.js` は上記パスへ `fetch` する（同一オリジン・Basic 認証セッション）。

### 12.2 公開 API（Runner・bot）

プレフィックス: **`/api/addons/meta-benchR1/`**（[アドオン規約](../addons/README.md)）  
認証: 各エンドポイント固有（`runnerSecret` / `benchToken`）

## 15. リスクと制約

| リスク | 対策 |
|--------|------|
| 100 bot + 10 WebRTC が手元 PC に重い | `botCount` 設定、Runner が推奨 max を宣言 |
| 本番プロセスへの負荷 | メンテ時間帯のみ、D-02 で新規流入を止める |
| mediasoup UDP が手元 PC から届かない | Cloudflare TURN（既存）利用、プリフライトで VC 系確認 |
| ±5〜7% を bot 系が外れる | レポートに「変動しやすいカテゴリ」と注記 |
| 既存ユーザーがベンチ中に残る | D-03 警告のみ。結果の解釈は運用者判断 |
| 再起動せずに addon 設定だけ変更 | P-07 で開始不可。手順（§4.2）を管理画面に表示 |
| ベンチ後に addon を戻し忘れ | 運用手順で再有効化・再起動を明記。レポートに実行時の有効 addon 一覧を記載（D-12） |
