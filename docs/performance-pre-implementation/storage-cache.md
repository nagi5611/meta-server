# 実装前段階プラン — ストレージキャッシュシステム

[索引に戻る](README.md)

## 目的

- 同一端末での **2 回目以降**のモデル・テクスチャ取得を高速化し、帯域と待ち時間を削減する（初回フルダウンロードは別問題）。

## スコープ（実装前に線引き）

| 含める | 含めない（別タスク） |
|--------|----------------------|
| 静的アセット URL のキャッシュ戦略 | CDN オリジンそのものの変更（Cloudflare 等は別議論） |
| キャッシュキーと無効化ポリシー | サーバ側のビルド成果物の署名基盤の全面刷新 |

## 調査・決定タスク（実装前）

1. **キャッシュ層の選択**: Service Worker + Cache API か、HTTP `Cache-Control` / ETag のみで足りるか。PWA 化の有無と整合させる。
2. **無効化**: モデル更新時にユーザーが古い GLB を見続けないための **バージョン付き URL**（クエリ or ファイル名ハッシュ）を既に使えるか。
3. **Three.js `THREE.Cache`**: メモリキャッシュとの役割分担（ディスク vs メモリ）。
4. **容量上限**: モバイルブラウザ・ストレージクォータの挙動確認。

## 既存コードとの接点（想定）

- モデル URL 生成（`buildEncodedModelUrl` 等）、Vite の `public` 配信、`server.js` の静的配信パス。

## リスク

- SW の更新サイクルとデプロイの不整合で「更新が反映されない」クレームが出やすい。

## 実装計画フェーズに渡す成果物

- 採用するキャッシュ方式 1 通りに決定した設計メモと、**無効化フロー図**（誰がいつキーを変えるか）。
