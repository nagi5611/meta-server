# 実装前段階プラン — LOD システム

[索引に戻る](README.md)

## 目的

- 距離に応じて **ポリゴン数・テクスチャ負荷**を下げ、低スペック GPU でのカクつきを抑える。

## スコープ

| 含める | 含めない（初期） |
|--------|------------------|
| ランタイムでの距離切替（`THREE.LOD` 等） | 自動メッシュ簡略化の品質保証まで含むフルパイプライン |
| アバター / ワールドのどちらから入るかの優先順位決定 | glTF `MSFT_lod` 等、ツールチェーン依存拡張の全面採用 |

## 調査・決定タスク（実装前）

1. **アセット供給**: LOD メッシュを **誰が・どのツールで**用意するか（Blender 手動 / glTF-Transform `simplify` / 別ファイル 2 本）。
2. **ワールド JSON / DB スキーマ**: 1 モデルに複数ファイルパスを持てるか。後方互換（LOD なし従来ワールド）の扱い。
3. **距離閾値**: ワールドスケール（単位・プレイヤー移動速度）に合わせた閾値の初期値。
4. **BVH・コリジョン**: 表示 LOD と **当たり判定用メッシュ**を分離するか（貫通・すり抜け防止との関係）。

## 既存コードとの接点（想定）

- `scene-manager.js` の `loadWorldModels`、ワールド定義のモデル配列。`player-manager.js` のアバター読み込み（[`lightweight-optimization-list.md`](../lightweight-optimization-list.md) の遠距離簡易表示と統合可能）。

## リスク

- アート制作コストで進まない。自動 simplify はシルエット破壊しやすい。

## 実装計画フェーズに渡す成果物

- 「第 1 段階はアバターだけ LOD」等の **スコープ確定**と、サンプルワールド 1 つ分の LOD 付きデータ仕様（JSON 案）。
